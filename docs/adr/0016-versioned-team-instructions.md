# Keep project working agreements as versioned team instructions

Accepted. This supersedes only the part of ADR 0013 step 3 about how the team remembers repository conventions and working agreements. Repository learning and delivery-policy changes remain separate work. Each Project has three text sections: repository conventions, engineering practices and delivery requirements. The Project page contains their current text, editor, history and comparison using the existing disclosure rows; there is no new page or navigation item.

A save appends an immutable, project-local numbered version with its full text, user/team source, optional originating Task and timestamp. Restoring copies an old version into a new version with a restore reference; it never rewrites history. Concurrent edits supply the version they started from and are rejected if it has changed. There are no editable historical records or deletion endpoints. Each Run pins the current version when created, before any asynchronous preparation. Version 0 means empty text; legacy Runs without a version stay explicitly unrecorded, rather than being attributed to today's text. Versions survive restarts and remain readable with the Run. Read-only owner conversations also pin their own current version and keep their existing read-only tools.

Role instructions, including the optional skill catalog, precede the team text, followed by the Task and turn input. The host explicitly states before the text that permissions, tools, onboarding authorization and reviews at pinned revisions are authoritative. Saving instructions does not modify any of those policies or the tools made available. Resumed sessions receive the version pinned for the new Run. This is working context, not an authorization source or a security sandbox.

The three sections together have a limit of 16,000 UTF-16 code units (the same count used by the browser's text fields). Over-limit saves fail with a clear error and preserve the current version; there is no truncation. This allows useful working agreements without unbounded prompt growth. Separate limits for each section were rejected because projects need different proportions. Comparison shows the complete before/after text of changed sections, stacked on phones, so deletions and context remain visible without introducing a diff dependency.

For task 3, a proposed change must remain separate from an adopted version: reserve a suggestion identity, base version, proposed sections, originating Task and interruption references, with pending/adopted/ignored outcomes. Adoption will append a version carrying `suggestionId` and `interruptionIds`; these provenance fields are already available to trusted Store writers. Ignored suggestions and subsequent restores must remain evidence for later retrospectives. Suggestions do not affect Run instructions until adoption. This task adds no automatic adoption, agent write tool or retrospective process. HTTP saves always identify the source as the user; clients cannot claim team provenance. Later repository learning can save through the trusted team boundary with its originating Task.
