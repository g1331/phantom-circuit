# Turn attributed engineering interruptions into versioned instruction suggestions

Accepted. Extends ADR 0016 with post-merge retrospectives and adoption. The shared interruption attribution module is the authority for both the report and retrospectives: only durable, same-Project, time-bounded evidence attached to a confirmed merge counts. Reason text alone cannot establish that the user intervened. Retrospectives read the complete Project event history, including records older than the UI's 200-event feed.

A confirmed merged Task with attributed interruptions gets at most one PM model turn. The attempt is saved before entering the Project's PM queue. The turn is independent of the liaison session, runs read-only from the repository after Task worktree cleanup, has no host tools, receives at most 36,000 context characters plus fixed instructions, and has a two-minute timeout. The result has a 24,000-character parse limit. Invalid, failed or interrupted turns remain recorded and are never retried automatically, including after restart. This deliberately trades occasional missed improvements for a predictable spending bound. Tasks with only product Clarifications get a no-change record without a model call. Other product decisions, authorization and spending are excluded by the PM verdict.

The PM can replace one section, including shortening or deleting it, or record that no rule helps. The existing combined 16,000-character limit applies to proposals as well as adopted instructions. A suggestion records its Task, base version, interruption references, category, explanation and proposed complete sections. A pending suggestion does not affect Runs. The Project page shows it next to team instructions using the existing disclosure records, and all pending suggestions contribute one item to the brief. Adoption appends an immutable team version; ignoring preserves the proposal. Restoring an older version marks adopted suggestions after that version as reverted while keeping the adopted version and its provenance intact.

Record-only is the default. A Project may explicitly enable automatic adoption for future suggestions; this does not adopt existing pending suggestions. Adoption always checks the base version, including in automatic mode, so intervening user edits cannot be overwritten. An automatic adoption produces one sentence in the liaison conversation. A stale proposal remains available for inspection and ignoring; there is no automatic rebase or extra model call.

Recent suggestion outcomes are bounded context for the PM; an exact duplicate of a prior section change in the same category is also suppressed against all persisted suggestions, including ignored and reverted ones. Comparing the changed section rather than the full proposed document preserves that decision across unrelated edits. This does not attempt semantic similarity or add an experience database.

Adopted versions expose `taskId`, `suggestionId`, `interruptionIds` and `interruptionCategories`. Interruption references use `message:`, `incident:`, `event:`, `clarification:` or `recovery:` prefixes. Engineering categories are `port_conflict`, `missing_evidence`, `unstable_check`, `base_resync` and `engineering`; non-adoption conclusions use `product`, `authorization`, `spending` or `no_rule`. These fields allow later reports to examine recurrence without treating a product choice as an engineering failure. Model labels are judgments about attributed evidence, not additional proof of user involvement.
